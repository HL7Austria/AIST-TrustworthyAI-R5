# PoC – FHIR AI Transparency Mapping

## Overview

This Proof of Concept (PoC) demonstrates how synthetic AI transparency metadata can be transformed into FHIR R5 resources.

The project simulates AI-assisted clinical risk assessment scenarios and maps the generated metadata into FHIR resources for transparency, provenance, auditability, and human oversight documentation.

The PoC is not intended for clinical use.
All generated data are synthetic.

---

# Project Structure

## `poc/input/`

Contains the synthetic base scenario.

### `base_case.json`
Defines:
- synthetic patient data
- encounter information
- vital parameters
- AI system metadata
- model card metadata
- legal context
- human reviewer metadata
- default mapping values

This file acts as the base input for all generated scenarios.

---

## `poc/config/`

Contains scenario-specific configuration files.

Example:
- `scenario_01.json`
- `scenario_02.json`

These files define:
- simulated AI output behavior
- human oversight behavior
- correction workflows
- patient explanation workflows

The configuration files are combined with `base_case.json` during metadata generation.

---

## `poc/output/metadata/`

Contains generated metadata scenarios.

Generated by the pipeline or manually by running:

```bash
python poc/src/simulate_ai_output.py
```

The generated metadata include:
- simulated AI outputs
- audit metadata
- provenance metadata
- human oversight metadata
- corrected observations
- patient explanations

These metadata files are the input for the FHIR mapping process.

---

## `poc/output/fhir/`

Contains generated FHIR R5 resources.

Generated by the pipeline or manually by running:

```bash
python poc/src/mapper.py
```

Each scenario receives its own folder.

Example:

```text
poc/output/fhir/sc-02-validation/
```

Generated resources may include:
- Patient
- Encounter
- Organization
- Device
- Observation
- Consent
- Provenance
- AuditEvent
- ArtifactAssessment
- Communication
- DocumentReference

---

## `poc/validation/results/`

Contains validation reports generated by the FHIR Validator.

The reports are created when the pipeline is executed with validation enabled.

---

# Python Files

## `poc/src/simulate_ai_output.py`

Generates synthetic metadata scenarios.

Responsibilities:
- calculate simplified NEWS2-inspired scores
- generate simulated AI outputs
- generate audit metadata
- generate provenance metadata
- generate human oversight metadata
- generate patient explanations

This file performs the simulation logic.

---

## `poc/src/news2_scoring.py`

Contains the simplified NEWS2-inspired scoring logic.

The implementation is intentionally simplified and is only used to create plausible synthetic outputs for the PoC.

It is not clinically validated.

---

## `poc/src/mapper.py`

Transforms generated metadata into FHIR R5 resources.

Responsibilities:
- create FHIR resource structures
- assign profiles
- create references
- map metadata fields into FHIR elements
- generate output JSON files

The mapper does not perform clinical decision making.
It only transforms already generated metadata into FHIR.

---

## `poc/src/fhir_utils.py`

Contains reusable helper functions for FHIR generation.

Examples:
- FHIR references
- CodeableConcept creation
- Quantity creation
- profile metadata
- utility functions for JSON handling

---

# Pipeline Script

## `poc/run-pipeline.ps1`

PowerShell script used to run the complete PoC pipeline from inside the `poc` folder.

By default, the script uses the existing IG package and executes:

1. metadata generation
2. FHIR resource mapping
3. validation of the generated scenario resources

The IG is not rebuilt by default.

---

# PoC Pipeline

## Run Pipeline with Existing IG Package

Use this command when the FSH profiles, extensions, CodeSystems, ValueSets, and IG example instances have not changed:

```powershell
.\run-pipeline.ps1
```

This generates the scenario metadata, maps the metadata to FHIR JSON resources, and validates the generated resources against the existing IG package:

```text
output/package.tgz
```

This is the default workflow for changes to the Python pipeline, scenario metadata, or scenario configuration files.

---


## Run Full Pipeline Including IG Build

Use this command after changes to the FSH files, profiles, extensions, CodeSystems, ValueSets, example instances, or `sushi-config.yaml`:

```powershell
.\run-pipeline.ps1 -BuildIG
```

This executes the full pipeline:

1. builds the IG using SUSHI
2. runs the IG Publisher
3. generates scenario metadata
4. maps metadata to FHIR JSON resources
5. validates the generated resources against the newly built IG package

The IG QA report is written to:

```text
output/qa.html
```

The IG package used for validation is written to:

```text
output/package.tgz
```

---
 
### PowerShell Execution Policy

If PowerShell blocks script execution, the pipeline can be started for a single execution using:

```powershell
powershell -ExecutionPolicy Bypass -File .\run-pipeline.ps1
```

To build the IG as part of the same execution:

```powershell
powershell -ExecutionPolicy Bypass -File .\run-pipeline.ps1 -BuildIG
```

This bypass applies only to the current command and does not permanently change the system configuration.

--- 
## Optional Pipeline Parameters

Clean previously generated PoC outputs:

```powershell
.\run-pipeline.ps1 -Clean
```

Run the pipeline without validation:

```powershell
.\run-pipeline.ps1 -SkipValidation
```

Validate only a specific generated scenario:

```powershell
.\run-pipeline.ps1 -ScenarioName sc-02-validation
```

Build the IG and clean previous PoC outputs before running:

```powershell
.\run-pipeline.ps1 -BuildIG -Clean
```

If local PowerShell script execution is blocked, the pipeline can be started with:

```powershell
powershell -ExecutionPolicy Bypass -File .\run-pipeline.ps1
```

or, including the IG build:

```powershell
powershell -ExecutionPolicy Bypass -File .\run-pipeline.ps1 -BuildIG
```

---

## When to Rebuild the IG

The IG should be rebuilt when changes were made to:

- FSH profiles
- extensions
- CodeSystems
- ValueSets
- example instances included in the IG
- `sushi-config.yaml`

If only the synthetic scenario metadata, scenario configuration files, or Python mapping logic changed, the existing IG package can usually be reused.

# Manual Workflow

The individual steps can also be executed manually. This is mainly useful for debugging.

## 1. Define Base Scenario

Edit:

```text
poc/input/base_case.json
```

---

## 2. Define Scenario Configurations

Edit or create files in:

```text
poc/config/
```

---

## 3. Generate Metadata

Run from the project root:

```bash
python poc/src/simulate_ai_output.py
```

Output:

```text
poc/output/metadata/
```

---

## 4. Generate FHIR Resources

Run from the project root:

```bash
python poc/src/mapper.py
```

Output:

```text
poc/output/fhir/
```

---

## 5. Validate Generated Resources

Run from the `poc/validation` folder:

```powershell
.\validate-scenario.ps1
```

# Validation

## `poc/validation/validate-scenario.ps1`

PowerShell script used to validate generated FHIR resources.

The script uses the official HL7 FHIR Validator CLI and validates generated scenario resources against the IG package.

Example:

```powershell
.\validate-scenario.ps1 -ScenarioName sc-02-validation
```

---

# FHIR Validator

The FHIR Validator `.jar` file is not included in the repository because the file size is too large for GitHub.

The validator must be downloaded manually.

Official validator:
- https://github.com/hapifhir/org.hl7.fhir.core/releases

Example:

```text
validator_cli.jar
```

Recommended location:

```text
tools/validator/
```

# Notes

- All patient data are synthetic.
- The PoC is intended for research and demonstration purposes only.
- The NEWS2-inspired scoring is simplified.
- No real AI model is used.
- No clinical claims are made.
- The generated outputs are deterministic simulations.
- The mapper does not infer clinical, legal, or workflow decisions.
- FHIR validation checks syntactic and structural conformance only.

---

# Purpose of the PoC

The purpose of this PoC is to demonstrate how:
- AI transparency metadata
- provenance information
- audit information
- human oversight documentation
- patient explanation information

can be represented using FHIR.
